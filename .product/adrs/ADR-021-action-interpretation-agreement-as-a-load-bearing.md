## Context

[ADR-017](ADR-017) makes action-interpretation pairing structural. [ADR-019](ADR-019) keeps the two sessions independent so their agreement carries signal. The natural consequence: **action-interpretation agreement is a measurable property of the system from session 1**, and it is the cleanest available proxy for "are the roles doing what we think they are?"

Phase C will operationalize fitness functions broadly. This ADR declares one fitness metric *now* — before Phase C — because (a) the data is being generated by every dispatch in Phase A, and (b) the metric is what would tell us if Phase A itself was a mistake.

## Decision

**Action-interpretation agreement is a declared, queryable, dashboarded fitness function from the start of Phase A.**

### Definition

Let `D` be the set of `DispatchGroup` artifacts in the orchestration store with both a paired `ActionSession` (terminal status `completed`) and an `InterpretationSession` (terminal, with a `VerificationVerdict`). Let:

- `A(D)` = subset of `D` where the action session reported success (worker exit 0, action-side artifact written).
- `V_approved(D)` = subset of `D` whose verdict is `approved`.
- `V_amended(D)` = subset whose verdict is `amendment-required`.
- `V_rejected(D)` = subset whose verdict is `rejected`.

The metrics:

| Metric | Formula | Meaning |
|---|---|---|
| **Agreement rate** | `|A(D) ∩ V_approved(D)| / |A(D)|` | Of dispatches the action thought succeeded, what fraction did the verifier approve? |
| **Amendment rate** | `|V_amended(D)| / |D|` | How often does the verifier ask for changes? |
| **Rejection rate** | `|V_rejected(D)| / |D|` | How often does the verifier reject outright? |
| **False-success rate** | `|A(D) ∩ (V_rejected(D) ∪ V_amended(D))| / |A(D)|` | Of dispatches the action thought succeeded, what fraction did the verifier flag? *This is the load-bearing one.* |

All four are computable from SPARQL against the orchestration store with no additional schema.

### Why it is load-bearing

Without this metric, the framework's central claim ("paired action + interpretation produces self-correcting chains") is untestable. With it, we have a falsifiable hypothesis:

> If the verifier and the implementer agree 100% of the time, the verifier is redundant.
> If the verifier rejects ~50% of the implementer's "successes", the implementer is uncalibrated.
> If both above are stable across runs, something is wrong with the role definitions, not the model.

The target band for Phase A is informal: false-success rate non-zero and non-saturating. Phase C will set numeric thresholds and gate releases on them. Phase A's job is to make the data exist and be queryable.

### Surface in slice 2

The metric is computed on demand (slice 2) — no continuous dashboard yet. The CLI surface ([FT-025](FT-025)) exposes:

```bash
dec metrics agreement                    # over all completed dispatches
dec metrics agreement --since <iso-date> # windowed
dec metrics agreement --role implementer # per action role
```

Output is a small table with the four metrics and the underlying counts. SPARQL query lives in `crates/decision-cli/src/core/`-resident metric helpers; the feature module that exposes `dec metrics` consumes them.

### Why declare it now and not in Phase C

Phase C operationalizes fitness functions as a continuous-monitoring system (broadcast subscriptions, threshold alerts, meta-loop input). That is a substantial increment. The *individual metric* is independent: it can be defined, computed, and audited without the broadcast machinery. Declaring it now means:

- Phase A integration tests can assert "after N dispatches with M rejections, `dec metrics agreement` returns the expected fractions" — proving the metric is wired.
- The metric is recorded in the graph from session 1, so Phase C has historical data to threshold against rather than starting from scratch.
- The framework's central claim has measurement evidence accumulating from day one.

### What this is NOT

- Not a quality bar on individual sessions. A verifier rejecting a session is not a defect; it is the system working.
- Not a release gate (yet). Phase C decides if and how it gates.
- Not a model-quality metric. It is a *role-design* metric: it primarily measures whether the implementer's authority and the verifier's authority are coherently scoped, not whether Claude is "smart enough."

## Rejected alternatives

- **Defer all metrics to Phase C.** Rejected: the data is being generated; collecting it costs nothing extra. Discarding it would require us to re-run Phase A dispatches in Phase C to bootstrap the metric.
- **Define agreement only at the dispatch level (binary agree/disagree).** Rejected: collapses amendment-required and rejected into a single bucket, losing the signal that distinguishes "wrong in detail" from "wrong in kind."
- **Per-feature metric (e.g. agreement rate scoped to FT-007).** Rejected for Phase A: feature counts are small; the metric is noise. Aggregate first; slice later.
- **Use confidence scores from the verifier instead of binary verdicts.** Rejected: see [ADR-018](ADR-018) — confidence scoring is its own calibration problem; the verdict is the metric primitive.

## Consequences

**Positive:**
- The framework's central claim is measurable from day one.
- Phase C has historical signal to work with, not a cold start.
- Role-design errors surface as metric outliers, not as anecdotes.

**Negative / accepted costs:**
- The metric is *correlational*. Phase C needs more work to make it *prescriptive* (when does a rate change mean "fix the role" vs. "the data is noisy"?).
- A small SPARQL query surface in `core/` to maintain.

**Enforcement:**
- A slice-2 TC asserts the four metrics are computable via `dec metrics agreement` against a seeded store.
- A cross-cutting TC ([ADR-014](ADR-014)) under this ADR asserts no Phase A or Phase B feature can mark itself complete unless the metric is reachable (i.e. no silent removal of the metric surface).
